# Wedding Camera

結婚式のゲスト全員で撮る、デジタル使い捨てカメラ。
スマホのブラウザで開くだけで撮影でき、写真は共有アルバム（Google Drive）に集まります。

- フロント: 静的な PWA（`index.html` 1 枚 + Service Worker）。ビルド不要
- バックエンド: Google Apps Script（`/exec` の Web アプリ）
- 保存先: Google Drive のフォルダ

---

## 構成

| ファイル | 役割 |
|---|---|
| `index.html` | アプリ本体（HTML / CSS / JS すべて） |
| `sw.js` | Service Worker。回線が切れてもリロードで真っ白にならないように |
| `manifest.json` | ホーム画面に追加したときの見た目 |
| `config.js` | **コミットされません。** GAS の URL・トークン・Drive フォルダ |
| `config.sample.js` | `config.js` のひな形 |
| `GAS_変更点.md` | バックエンド（コード.gs）に当てるパッチ。第 1〜3 弾は適用済み |
| `GAS_変更点_第4弾.md` | **未適用。** 当日に効く 6 件（エラー分類・二重登録・受付期限の UTC 解釈など） |

## ローカルで動かす

`file://` でも起動はしますが、**カメラと Service Worker は https か localhost でないと動きません。**
必ずローカルサーバー経由で開いてください。

```bash
cp config.sample.js config.js   # 値を埋める（Windows は copy）
npx serve .                     # または python -m http.server 8000
```

`http://localhost:3000`（serve の場合）を開きます。

1. **Pages のソースを Actions にする**
   Settings → Pages → Build and deployment → Source を **GitHub Actions** に変更

2. **Secrets を 3 つ登録する**
   Settings → Secrets and variables → Actions → New repository secret

   | 名前 | 中身 |
   |---|---|
   | `WEDCAM_API_URL` | GAS の `/exec` URL |
   | `WEDCAM_API_TOKEN` | GAS の `generateApiToken()` が出した値 |
   | `WEDCAM_DRIVE_FOLDER_URL` | 共有アルバムの Drive フォルダ URL（任意） |

### 以降

`main` に push すれば自動で配信されます。
公開先は `https://<ユーザー名>.github.io/wedding-camera/` です。

> **リポジトリ名を変えると URL が変わり、配布済みの QR コードが全部死にます。**
> QR を作る前に名前を確定させてください。

## トークンの扱いについて

`API_TOKEN` は最終的にゲストのブラウザへ配られるため、**本質的な秘密にはできません。**
目的は「URL を拾った自動スキャンの流れ弾を弾く」ことだけです。

このリポジトリは公開ですが、`config.js` を `.gitignore` して Actions で生成することで、
**リポジトリのソースにも git 履歴にもトークンが残らない**ようにしています。
GitHub のコード検索やスキャン bot に拾われないための措置です。

実際の防御はサーバー側で行ってください。

- 保存先フォルダ所属チェック（`getFileInTargetFolder`。実装済み）
- 挙式日を過ぎたらアップロードを閉じるフラグ（実装済み。下記「写真の受付を締め切る」）

写真を削除する機能は**意図的に持たせていません**。Drive のフォルダを直接開けば
新郎新婦の判断で削除できるため、アプリ側に削除 API を置かないほうが安全です。

**1 日あたりのアップロード枚数に上限は設けていません**（方針として無制限）。
実質的な上限は Google 側のクォータ（GAS の 1 日あたり実行時間・UrlFetch 回数、
Drive の空き容量）で、これらはアプリ側からは変更できません。

トークンを変えるときは **GAS のスクリプトプロパティと GitHub Secrets の両方**を更新してください。

## バックエンド（GAS）

`GAS_変更点.md` のパッチを当ててください。撮影時刻順の並びと二重登録の防止は、
フロントとバックエンドが揃って初めて効きます（フロントだけ先に出しても壊れません）。

**`GAS_変更点_第4弾.md` はまだ適用していません。** 当日に効く 6 件が入っています。
特に次の 2 つは、当日起きると原因に辿り着けません。

- 送信エラーが全部同じ文言なので、`FOLDER_ID` の typo でも全ゲストが 5 回ずつ再送する
- `setUploadDeadline('2026-09-05')` と**日付だけ書くと UTC 解釈で当日の朝 9 時に受付が閉まる**

反映後は必ず **デプロイを管理 → 鉛筆アイコン → バージョン「新バージョン」→ デプロイ**。
「新しいデプロイ」を作ると URL が変わり、配布済みの QR が全部死にます。

## 新郎新婦向けの操作

### 写真の受付を締め切る

GAS エディタで実行します。

```
setUploadDeadline('2026-09-05T23:59:59+09:00')   期限を設定
setUploadDeadline('')                            解除（無期限）
```

期限を過ぎると、表紙に案内が出てカメラボタンが押せなくなり、サーバー側でも
アップロードを拒否します。**アルバムの閲覧と保存はそのまま使えます。**

案内文を変えたいときは、スクリプトプロパティ `UPLOAD_CLOSED_MESSAGE` に文章を入れてください。

> 受付を閉じた時点で未送信の写真が残っていた場合、ゲストは表紙の
> 「端末に保存する」で自分の端末に取り出せます。

> **`setUploadDeadline()` には必ず時刻まで書いてください。** `'2026-09-05'` のように
> 日付だけを渡すと、JavaScript の仕様で **UTC** として解釈され、JST の当日**朝 9 時**に
> 受付が閉じます。`GAS_変更点_第4弾.md` の D を適用すると自動で補完されます。

### 式が終わったらアルバムを閉じる

**受付を締め切っても、アルバムの閲覧は永久に開いたままです。** `UPLOAD_DEADLINE` は
アップロードだけを止めるもので、`getAlbum` / `getSingleBase64` には効きません。
さらにサムネイルを表示するために Drive フォルダを「リンクを知っている全員」で
共有しているため、**URL を受け取った人は誰でも全写真の原本をダウンロードできます。**

式のあと、次の 3 つをやってください。1 つでも残すと公開されたままになります。

1. **書き込みを止める** — GAS エディタで `setUploadDeadline('2026-09-06T00:00:00+09:00')`
2. **API を閉じる** — GAS の「デプロイを管理」→ 鉛筆 →
   「アクセスできるユーザー」を **自分のみ** に変更（URL は変わりません）
3. **Drive の共有を戻す** — 保存先フォルダを右クリック → 共有 → **「制限付き」**

写真は新郎新婦の Drive に残るので、閉じても中身は失われません。
あとでゲストに配るときは、Drive から改めて共有リンクを出すか、まとめて渡してください。

> ゲストには名前登録時に「URL を開いた人全員が見られる／招待客以外の目に触れることがある」
> と表示しています。式のあとまで開けたままにするのは、その説明の範囲を超えます。

## ズームについて

シャッターの右に倍率ボタン（`1.0×`）が出ます。押すと 1.0 → 1.5 → 2.0 → 1.0 と
回り、ピンチでも無段階に寄れます。ピンチだけでは気づかれないので、
必ず見えるボタンを併置しています。

**寄り方は端末で 2 通りに分かれます。**

| | 端末側ズーム | デジタルズーム |
|---|---|---|
| 使う端末 | Android Chrome など | **iPhone 全機種**、その他 |
| 仕組み | `applyConstraints({ zoom })` | 中央を切り出す |
| 画質 | 落ちない | 寄るほど落ちる |
| 録画への反映 | 効く | **効かない** |
| 動画モード | 使える | ボタンを隠す |

iOS Safari は `zoom` 制約に未対応です。iOS では Chrome も Firefox も WKWebView
なので、ブラウザを変えても同じです。デジタルズームは `MediaRecorder` が CSS では
なくトラックを録るため録画に乗りません。プレビューだけ寄って録画は寄らない、
という食い違いを避けるため、**デジタルズームのときは動画モードでボタンを隠し、
倍率も等倍へ戻します。**

### 撮影解像度を写真と動画で分けている理由

| | 希望値 | 場所 |
|---|---|---|
| 写真 | 3840×2160 | `CONFIG.CAPTURE_IDEAL_WIDTH / HEIGHT` |
| 動画 | 1920×1080 | `CONFIG.VIDEO_IDEAL_WIDTH / HEIGHT` |

デジタルズームは元が大きくないと寄るほど粗くなるため、写真だけ 4K を要求します。
動画を 4K にしないのは、1.5Mbps を 4K に当てると 1 画素あたり 0.02bit しか無く
ブロックだらけになるうえ、会場で 4K を符号化させると発熱と電池消費が跳ね上がる
ためです。

保存サイズの実測（iPhone 15 相当・縦持ち）:

| 倍率 | 保存サイズ |
|---|---|
| 1.0× | 1200×1600 |
| 1.5× | 1080×1440 |
| 2.0× | 810×1080（＝ 4K 化する前の等倍と同値） |

**2 倍まで寄っても以前より粗くなりません。** ただし例外があり、端末が縦長フレーム
（2160×3840 など）を返している状態で横持ちすると、1.55 倍を超えたあたりで
以前の画素数を下回ります（自動回転オフで横に構えたときに起こりえます）。
それ以外の組み合わせでは 2.0〜3.0 倍まで以前以上です。

> **モードを切り替えると、ストリームを取り直します。**
> 起動 4K → 動画モード（取り直さない）→ 録画開始 1080p＋音声 → 写真へ戻す 4K、
> の順です。最後の「写真へ戻す」を忘れると、**動画を 1 本撮ると以降その端末の
> 写真だけ解像度が半分以下になります**（実際に起きた不具合です）。
> 解像度の指定は `videoConstraints()` に一本化してあるので、
> `getUserMedia` を呼ぶ箇所で直に書かないでください。

> **撮影範囲の計算で `getBoundingClientRect()` を使ってはいけません。**
> デジタルズームは CSS の `transform: scale()` なので、この値は拡大後の枠を
> 返します（2 倍で幅 1254 → 2509）。そのまま使うと、寄っているのに広く切り出して
> しまいます。`offsetWidth` / `offsetHeight` は `transform` の影響を受けないので、
> `captureFrame` はそちらを使っています。

## 動画について

カメラ画面の「写真 / 動画」で切り替えます。MediaRecorder が使えない端末では
切り替え自体を出しません。

**制約は容量です。** GAS へは Base64（1.33 倍に膨らむ）で送るため、長い動画ほど
会場の回線で失敗します。既定は次のとおりです。

| 設定 | 既定値 | 場所 |
|---|---|---|
| 最大の長さ | 15 秒 | `CONFIG.VIDEO_MAX_SEC` |
| ビットレート | 1.5 Mbps | `CONFIG.VIDEO_BITS_PER_SEC` |
| 送信の上限 | 10 MB | `CONFIG.VIDEO_MAX_BYTES` |
| サーバー側の上限 | 10 MB | GAS の `MAX_UPLOAD_BYTES_VIDEO` |

15 秒 / 1.5Mbps で 1 本 3MB 前後です。**長さを変えるときは `VIDEO_MAX_SEC` だけ**
直せば済みます（3MB 前後なので 10MB の上限には届きません）。

> **2 つの上限は必ず「フロント ≦ サーバー」にしてください。**
> フロントのほうが高いと、通らない動画を会場の回線で送り切ってから拒否されます。
> 25MB は Base64 で 33MB になり、上り 2Mbps なら 2 分以上かかります。
> 以前はフロント 25MB／サーバー 30MB だったため、サーバー側の上限が
> 一度も発動していませんでした。

- 音声はマイクの許可が要るため、**動画モードに入ったときだけ**要求します。
  拒否された場合は音声なしで録画を続けます。
- 送信中は画面上部のバッジに「動画 3.1MB を送信中 12秒 ・残り 2 件」と出て、
  帯が流れます。別の要素を出して撮影画面を覆わないためです。

> **パーセント表示ができない理由**
> GAS は 302 リダイレクトを返すため、XMLHttpRequest では CORS 越しに追えず
> 送信自体が失敗します。さらに `upload.onprogress` を付けた時点で
> プリフライト（OPTIONS）が発生し、GAS は OPTIONS に応答できません。
> つまり**送信バイト数を取得する手段がありません**。偽のパーセンテージを
> 出すより害が少ないため、経過時間と容量を正直に見せる方式にしています。
> アップロードは必ず `fetch` を使ってください（XHR に変えると全滅します）。
- 再生は Drive のプレビューを使います（全体をダウンロードせずに済むため）。
- **動画はまとめて保存の対象外**です。1 本で写真数十枚ぶんの容量になり、
  5 件ずつ Base64 で取ると GAS の実行時間にも通信にも収まらないためです。
  動画をタップして 1 本ずつ保存してください。
- 端末に既にある動画も「端末の写真をアップロード」から送れます（再エンコードは
  しないので、25MB を超えるものは弾かれます）。

## まとめて保存について

**ねらいは「選んだ写真が JPG のまま 1 枚ずつ端末に入ること」です。**
ZIP は 1 つの塊で落ちるだけなので、アルバムの一括保存からは外しました
（表紙の「端末に保存する」と未送信分の書き出しでは今も使っています）。

| 選択肢 | 入り先 | 出る条件 |
|---|---|---|
| **写真アプリに 1 枚ずつ保存** | **カメラロール** | `canShare({files})` が真 |
| **1 枚ずつダウンロード**（iPhone では「ファイル」アプリに保存） | ダウンロード / ファイルアプリ | 常に |
| Google ドライブのフォルダを開く | 共有フォルダ | `DRIVE_FOLDER_URL` があるとき |

おすすめのほうを JS で上に並べ替えます。**iPhone は Web Share が上**（カメラロールに
入るのはこれだけ）、それ以外は順次ダウンロードが上です。

### 何枚まで渡せるかは端末に聞きます

`share()` の上限は**枚数ではなく主に合計サイズ**で決まります。固定値で割ると、本当は
一度に渡せる端末でも無駄に何回も分けることになります。`largestShareableCount()` が
実際のファイルで `canShare` を二分探索し、通る最大枚数を求めます。

- 端末に制限が無ければ **40 枚でも 1 回**で渡します（分割表示すら出ません）
- 上限があれば、その枚数ずつ「1 / 4」「2 / 4」と続けて渡します
- `canShare` が真でも `share()` が落ちることがあるため、**自動で半分に割り直して
  再試行**します（40 → 20 → 10 と落ちて通った時点で続行）

> **`share()` はループで呼べません。** iOS は 1 回ごとにユーザーのタップを要求し、
> 2 回目は `NotAllowedError` になります。しかも毎回 iOS 自身の共有シートが出るので、
> 「裏側で 1 枚ずつ share する」は実現できません。束ごとにボタンを押してもらう
> 作りなのはこのためです。

> **以前は枚数を理由に「写真アプリに保存」を隠していました。** その結果、21 枚以上を
> 選ぶと ZIP と Drive しか残らず、Drive を開いた先が「マイドライブ」になる、という
> 詰まり方をしていました。**枚数で隠さないでください。**

束の途中では他の選択肢を隠します（別の方法に移られると取りこぼすため）。
シートを閉じたら `resetSaveSheetState()` で必ず戻してください。

### 写真は GAS を通さず Google から直接受け取ります

**保存の速さはここでほぼ決まります。**

アルバムのサムネイルに使っている `https://drive.google.com/thumbnail?id=…` は
CORS を返さないので `fetch` できません。ところが、**この URL の転送先である
`https://lh3.googleusercontent.com/d/<ID>` は `Access-Control-Allow-Origin: *`
を返します。** 転送元が塞がっていただけで、配信元は最初から開いていました。

本番のオリジンから実測した結果です。

| | 1 枚 | 34〜40 枚 | GAS の呼び出し |
|---|---|---|---|
| GAS 経由（以前） | 5,558 ms | 約 222 秒 | 40 回 |
| **直接（いま）** | **約 400 ms** | **約 3 秒** | **0 回** |

- 原本とバイト単位で完全一致（10 枚を SHA-1 で照合し 10/10 一致）。画質は落ちません
- Google に未ログインの端末でも取れます（フォルダが「リンクを知っている全員」で
  共有されているため。サムネイルが見えている時点で本体も見えます）
- **保存のあいだ GAS を 1 回も呼びません。** 当日 60 台が同時に保存しても、
  Apps Script の同時実行 30 本は撮影と一覧のために丸ごと空いたままです

**動画には使えません。** lh3 は動画 ID に対して mp4 ではなく静止画のポスターを
返します（実測 1152KB の mp4 に対し 114KB の `image/jpeg`）。動画はこれまでどおり
GAS 経由です。

この URL の形は Google が文書化したものではないので、いつか変わる可能性があります。
**失敗したら黙って GAS 経由に落ちます**（`fetchAllBlobs` の第 2 段）。
その場合でも以前と同じ動きに戻るだけで、保存できなくなることはありません。

#### 429（多すぎます）への備え

lh3 は叩きすぎると **HTTP 429** を返します。8 並列で 34 枚を投げたら 4 枚が
弾かれました。同時本数を 3 本まで落としても 429 は残るので、回線ごとの
短時間の回数も見ているようです。三段構えにしてあります。

1. 並列は **4 本**（`DIRECT_CONCURRENCY`）
2. 429 / 503 なら待って取り直す（最大 3 回。`Retry-After` があれば従う）
3. 続けて 6 枚失敗したら見切って、**残りを丸ごと GAS へ**（`DIRECT_GIVEUP_STREAK`）

検証済みです。通常時は 34 枚が GAS 呼び出し 0 回で完走。lh3 を全面的に塞ぐと
直接の試行 27 回で見切り、`getBatchBase64` 7 回に切り替えて 34 枚とも保存しました。

### 取得は 1 枚ずつ、保存も 1 枚ずつ

順次ダウンロードは **1 枚取れたらすぐ保存**します。まとめて取ってから保存すると、
途中で失敗したときに何も保存されないまま終わります。

GAS へ落ちたぶんのまとめ取り（`getBatchBase64`、5 枚ずつ）が失敗したときは、
**1 枚ずつ取り直します**。
5 枚まとめては 3MB 前後になり、混雑時はそれだけで落ちます。1 枚なら通ることが多く、
失敗しても 1 枚で済みます。それでも取れなかったぶんは覚えておき、
**「取得できなかったぶんをやり直す」でそこだけ**再取得できます。

> 以前は 5 枚まとめての 1 回の取りこぼしで 5 枚まとめて欠落し、しかも取れたぶんも
> 保存されないまま「N 枚は取得できませんでした」で終わっていました。

### カメラロールへは Web から書き込めません

**写真アプリに書き込む API は存在しません。** `download` で保存したものは
必ず「ファイル」アプリに入ります。カメラロールに入れられるのは、共有シートで
「画像を保存」を選んだときだけです。iPhone で Web Share を上に置いているのは
このためです。

なお **「iOS は 2 枚目以降のダウンロードを必ず止める」とは言い切れません。**
Safari の版によって挙動が変わり、複数ダウンロードの許可を尋ねることもあります。
止められてもこちらからは検知できないので、iPhone では間隔を 700ms に伸ばし、
完了時に「『ファイル』アプリをご確認ください。枚数が足りないときは写真アプリの
ほうをお使いください」と伝えています。

### Drive のフォルダが「マイドライブ」になる件

iOS はフォルダの URL で Drive **アプリ**を起こします。そのアプリにログイン中の
アカウントにフォルダの権限が無いと、マイドライブが開きます。リンク共有のフォルダで
普通に起きます。

`usp=sharing` を付けて改善を図っていますが、**これで直らない端末もあります。**
説明文とトーストで「ブラウザで開き直してください」と伝えています。アプリ側の挙動なので、
Web からは確実に制御できません。

## 操作子の記号について

**ボタンの中の記号を「文字」で書かないでください。** ◀ ▶ ↻ ✕ ✓ ☑ のような記号は、
単色 SVG をマスクとして敷く仕組み（`.ui-icon` + `.icon-*`）に載せます。

```html
<button class="btn-icon-round ui-icon icon-refresh" aria-label="…"></button>
<button class="btn-album-back ui-icon icon-prev">モード選択</button>
```

### 文字で書くと必ずずれる理由

1. **flex の中央寄せが揃えるのは「行ボックス」で、字面（インク）の中心ではありません。**
   body から継承した `line-height: 1.7` が行ボックスを膨らませ、そのぶん記号が
   上下にずれます
2. **iOS では `◀`（U+25C0）`▶`（U+25B6）が絵文字として描かれます。**
   絵文字は字面の大きさも位置も文字と違い、しかも `color` が効きません
3. **`--dot-font`（DotGothic16）はこれらの記号を持っていません。**
   iOS には MS Gothic も無いので monospace まで落ち、書体ごとにずれ方が変わります

`↻` `×` `✕` は絵文字にはなりませんが、字面が em ボックスの中心にないため同じくずれます。
`🔄` は絵文字なので `color` がそもそも効きません。

### 図形を足す・直すときの決まり

- viewBox は `0 0 24 24`。**インクの外接矩形が 24×24 の中心に来るよう**座標を取ります
- 色は付けません。`currentColor` で塗られるので、ボタンの `color` がそのまま効きます
- **直したら必ず測ってください。** ブラウザで実際に描画し、
  `getBoundingClientRect()`（線幅を含みます）で全図形の外接矩形を合わせ、
  viewBox の中心との差が 0 になることを確かめます
- 非対称な図形は群ごと `transform="translate(…)"` でずらして合わせます
  （更新アイコンは円弧と矢頭が非対称なので `translate(0 1.4)`。この 1.4 は実測値です）
- ボタン側には `line-height: 1` と、記号だけなら `padding: 0` を入れます。
  大きさは `--icon-size` で指定します

### 絵文字のまま残しているもの

📷 🎬 ⬇️ 📲 📥 📤 🖼️ 💌 ✨ ⚠️ など、**文字ラベルと並ぶ装飾**は絵文字のままです。
円の中心に単独で置くものではなく、表紙の賑やかさを担っているためです。

> **絵文字を使うなら、異体字セレクタ U+FE0F を付けてください。**
> 付けないと iPhone では色付き絵文字・Android では単色の文字になり、
> 同じ並びの中で調子が割れます（`⏸` がこれで割れていました）。

## 端末チェック（対応機種の確認）

**[`check.html`](check.html) を確認したい端末の Safari で開いてください。**
`https://<公開 URL>/check.html` です。アプリからは辿れないので、ゲストの目には触れません。

このアプリが必要とする機能を 1 つずつ実際に確かめ、`[OK] / [代替] / [NG]` で出します。
下の「結果をコピー」でそのまま貼り付けられます。

「カメラを確かめる」「録画を確かめる」を押すと、**静的には分からないことも実測します。**

- getUserMedia が実際に返した解像度（**4K を要求して本当に 4K が返るか**）
- 端末側ズーム（`applyConstraints` の `zoom`）が使えるか
- 背面カメラが何台見えるか（広角・超広角が個別に見えれば画質を落とさず寄れます）
- 対応する録画形式と、15 秒あたりの見込み容量
- 試し撮りの絵が真っ黒でないか

**実質の下限は iOS 14.5 です。** 代替を用意していない機能が 1 つだけあり、
それが flexbox の `gap`（21 箇所）だからです。

| `dvh` | 15.4 | あり（`vh`） |
| `crypto.randomUUID` | 15.4 | あり（`getRandomValues` → `Math.random`） |
| `screen.orientation` | 16.4 | あり（`window.orientation` → 画面比） |

## アルバムの読み込みが遅いとき

**まず知っておいてほしいこと。この症状は「遅い」ではなく「断続的に失敗している」です。**
同じ endpoint の実測値です。

| 状況 | 結果 |
|---|---|
| 落ち着いているとき | **1.7 秒**で 30 件（正常） |
| 短時間にアクセスが集中したあと | 27 秒 → **HTTP 404**（Google のエラーページ） |
| 同上 | 140 秒 / 810 秒 |

Apps Script は集中アクセスで絞られます。**式当日にゲストが一斉にアルバムを開く状況が
まさにこれです。**

### フロント側でやっていること

1. **前回の一覧を端末（localStorage）に残し、待たずに先に描きます。**
   開いた瞬間に写真が出て、届き次第そのまま最新に置き換わります。
   30 件で 12KB 前後なので localStorage に収まります。
2. **アルバムだけ諦めるのを早くしています**（`ALBUM_TIMEOUT_MS` 15 秒 ×
   `ALBUM_ATTEMPTS` 2 回）。共通の `TIMEOUT_MS`（25 秒）× `READ_ATTEMPTS`（3 回）
   だと待機込みで**最悪 79 秒**、「読み込んでいます…」だけが続きます。
   前回ぶんが先に出るので、早く諦めて構いません。
3. 5 秒経つと「混み合っています…」に文言が変わります（`ALBUM_SLOW_HINT_MS`）。
4. 更新に失敗しても**見えているものを消しません。** 全面の「読み込めませんでした」
   ではなく、上に一行だけ警告（`.album-notice`）を出します。

> **控えを描いたあと、最新が届いたら必ず配列を作り直してください。**
> 重複除外（`known` の Set）に通すだけだと、「控えにあって最新に無い写真」
> （消された・並びが変わった）が居座り、古いものが混ざった一覧になります。
> `state.albumFromCache` を見て、`state.albumImages` を空にしてから詰め直します。

### サーバー側（GAS）でやっていること

`ALBUM_CACHE_SEC`（20 秒）のキャッシュキーには**アップロードごとに進む世代番号**が
入っています。披露宴中は撮影が途切れないため、**このキャッシュはほぼ一度も効かず、
ゲストの読み込みが毎回 Drive への実アクセスになります。**

そこで**集中をまとめるための第 2 のキャッシュ**を入れています
（`ALBUM_BURST_SEC`、既定 10 秒）。世代番号を含まないキーなので、
アップロード直後でも 10 秒だけは同じ結果を配ります。

| | 世代つきキー | 集中をまとめるキー |
|---|---|---|
| キー | `album_v<世代>_<件数>_<token>` | `album_burst_<件数>_<token>` |
| 期限 | 20 秒 | 10 秒 |
| アップロードで無効化 | される | **されない** |
| 役目 | 平常時の使い回し | 同時アクセスを Drive 1 回にまとめる |

**80 人が同時に開いても Drive への呼び出しは 10 秒あたり 1 回**に収まります。
代わりに、撮った写真がアルバムに出るまで最大 10 秒かかります。
キャッシュ期間を伸ばす（例 45 秒）方法もありますが、そちらは「撮ったのに
出てこない」時間がそのまま伸びるため採っていません。

## アルバムのプレビュー（前後移動）

写真をタップすると拡大表示になり、左右の `◀ ▶` で隣へ移動できます。ヘッダー右に
「3 / 40」と現在位置が出ます。PC では `←` `→` も使えます。

> **現在位置は添字ではなく id（`state.modalPhotoId`）で持ちます。**
> `state.albumImages` は ↻ の読み直しで丸ごと作り替えられるため、添字で覚えると
> 同じ番号が別の写真を指します。押すたびに `findIndex` し、**見つからなければ
> 黙って隣へ飛ばさず閉じます**（`list[-1]` は `undefined`、`list[0]` は
> 「一番新しい写真に飛ぶ」という別の壊れ方になります）。
> 読み込み中は一覧が一瞬空になるので、そのときだけ閉じずに待ちます。

- 末尾で ▶ を押すと、**続きを読み込んでから**進みます。1 ページ 30 枚なので、
  式の写真なら必ずここに届きます。読み込み中に押された場合は何もしません
  （`loadAlbum` は `isAlbumLoading` で黙って return するため）。
- カウンタの `+` は「まだ読み込んでいない先がある」という意味です。総数を
  断定すると、読み込み後に数が増えて食い違います。
- 閉じると、グリッドが**最後に見ていた写真まで**送られます。20 枚先まで見てから
  閉じたときに、続きからタップできるようにするためです。

### 保存の途中で隣へ移ったとき

`state.singleSave` に保存の進み具合（`fetching` / `ready`）を持ち、戻ってきたら
復元します。**これが無いと次の 3 つが起きます。**

1. 取得完了時にボタンを書き換える分岐へ、前の写真の通信が返ってくる。
   画面は隣の写真なのに、押すと前の写真が保存される
2. 取得中に離れて戻るとボタンが押せる状態に戻り、**10MB の動画を二重取得**する
3. 「📲 タップして写真に保存」まで進んだのに離れると黙って捨てられ、本人は
   「保存」の文字を 2 回見ているので**保存できたつもりになる**

> **iPhone が通るのは Web Share の分岐です。** 以前ここには
> 「まだ同じ写真か」の確認がありませんでした（確認があったのは
> `downloadBlob` 側のタイマーだけ）。`saveSinglePhoto` に手を入れるときは、
> **`await` の後にボタンへ触る箇所すべてで `button.dataset.photoId` を確かめて
> ください。**

閉じたときは控えを捨てます（◀▶ で離れるだけなら残します）。動画は 10MB あるので、
閉じても抱え続けると端末のメモリを圧迫するためです。

### 見た目で気をつけている点

- `◀ ▶` は写真の上に乗ります。写真の明るさは予測できないので、塗りは濃紺の
  不透明寄り、枠はシアンにして、明るい写真では塗りが・暗い写真では枠が
  「そこに在る」ことを伝えます。
- **端で押せないときに `opacity` を使ってはいけません。** 要素ごと薄まるため、
  白飛びした写真の上では濃紺の塗りまで透けて「ボタンが無い」ように見えます。
  塗りは不透明のまま残し、文字の色と発光を落として示します。
- 次の 1 枚が届くまで前の写真を薄く表示します。会場の回線では数秒かかるため、
  そのままだと「押したのに変わらない」と受け取られます。

### 見送ったもの

**左右スワイプは入れていません。** ピンチ拡大後に写真を横へ動かす操作が
「次の写真へ」と解釈されて拡大中の写真が消えること、動画のコマではタッチが
クロスオリジンの iframe で止まって効かないことの 2 つが理由です。効くコマと
効かないコマが混ざると「効いたり効かなかったり」に見えます。

## 送信の停止と、端末への自動保存

### 送信が固まったとき

送信中は画面上部のバッジに **✕** が出ます。押すと実行中の通信を打ち切って停止します
（動画のタイムアウトは 3 分あるので、これが無いと待たされ続けます）。
写真はキューに残るので、あとから再送も端末保存もできます。

どうしても送れない場合は、表紙の **「送信待ちを破棄する」**（2 段階確認）で
キューを空にできます。端末側の控えは消えません。

### 保存した写真が 90 度倒れる場合

「画面の自動回転」がオフのまま端末を横に構えると、**プレビューは正しく見えるのに
保存した写真だけが倒れます。** 画面の中身も端末と一緒に物理的に回るため、
カメラ映像の回転と打ち消し合ってプレビューは正常に見えますが、
保存されるピクセルは画面座標系のままだからです。

画面の向きと端末の実際の向き（傾きセンサー）が食い違うときだけ、保存時に
90 度回して直しています。自動回転がオンなら両者は一致するので何もしません。

**端末の向きは重力ベクトルから判定しています**（`applyDeviceOrientation`）。
`deviceorientation` の `gamma` は仕様上 `[-90, 90)` に畳まれて報告されるため、
`|gamma|` と `|beta|` を比べる方法では判定できません。同じ姿勢でも「画面の仰角」
（見下ろすか見上げるか）で値の組が変わり、

- 少し見下ろすと、画面内で 30 度傾けただけで「横持ち」に化ける
- 少し見上げると、本当に 90 度倒しても「縦持ち」のまま

という具合に、答えと無関係な要素で結論が変わってしまいます。
重力ベクトルの画面内成分からロール角を直接求めれば、仰角に依存しません。
判定は 60 度超で横・30 度未満で縦、その間は前回値を維持（ヒステリシス）です。

> もし補正後の写真が**逆向きに**倒れる端末があれば、`CONFIG.ROTATION_SIGN` を
> `1` から `-1` に変えてください。端末ごとの符号差を吸収するための逃げ道です。
> ただし、まず「そもそも補正が必要な状況か」（自動回転がオフか）を確認してください。

### 撮影データの端末への自動保存

撮った写真・動画は、送信の成否とは**別に必ず端末内へ控えます**（IndexedDB）。
送信が成功しても消しません。表紙の **「この端末で撮った ○ 件を保存」** から、
写真アプリ（20 件まで）または ZIP で取り出せます。

> **なぜ自動でカメラロールに入らないのか**
> Web ページから端末の写真ライブラリへ無音で書き込む API は存在しません。
> `<a download>` は iOS では自動実行がブロックされ、Web Share API は
> 毎回ユーザーのタップを必要とします。そのため「保管は自動・取り出しは 1 タップ」
> という形にしています。
>
> 控えは合計 300MB（`CONFIG.ARCHIVE_MAX_BYTES`）を超えると古いものから消えます。
> 端末の空き容量を食い潰さないための歯止めです。

## 端末の向きについて

**Web ページから OS の「画面の自動回転」をオンにする方法はありません。** これはブラウザに
API が存在しない領域です。自動回転がオフだと、端末を横に構えても画面は縦のままで、
`screen.orientation` も縦のままになります。

そのため 2 段構えにしています。

1. カメラ画面に「自動回転をオンに」の案内を出す（OS 別の手順つき・一度閉じたら出ない）
2. **傾きセンサーで物理的な向きを判定する** — 画面が回らなくても、端末を横に倒せば
   横写真になります。Android は許可不要で自動的に有効。iOS 13 以降は許可が要るため、
   案内内のボタンを押したときだけ要求します（ゲスト全員に許可ダイアログを見せないため）。

## 当日の運用メモ

- 緊急修正を push した場合、HTML は network-first なのでゲストのリロードで反映されます
- 未送信の写真は端末の IndexedDB に残ります。ページを閉じても消えません
- 送れない写真は表紙画面の「端末に保存する」で取り出せます
